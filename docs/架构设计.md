# 大量子 · 网络观点分析工具 · 架构设计

> 名字取自《超新星纪元》里那台为孩子们做信息筛选的超级计算机。
> 它的核心能力不是「统计」，是**从噪音中提炼 + 分类呈报**。

---

## 一、调研结论：哪些能复用，哪些必须自研

调研了 6 个直接相关的开源项目。结论如下。

### 结论速览

| 环节 | 现有开源项目 | 能否直接复用 | 决策 |
|------|-------------|-------------|------|
| 多平台评论采集 | 见下方逐平台清单 | ⚠️ 无单一方案覆盖全部 | **做适配器层**，采集与分析解耦 |
| 事件级舆情研究报告 | BettaFish 微舆 | ⚠️ 是「报告生成器」不是「观点归类器」 | **不复用**，只借鉴报告结构 |
| 评论 → 话题/观点分类学 | **Jigsaw sensemaking-tools** | ⚠️ Apache-2.0 但强绑 Google 云 | **借思路**，不搬代码 |
| 主张聚类 + 报告 | Talk to the City (tttc-light-js) | ❌ 是 SaaS（Firebase+Redis+GCS+Pub/Sub） | **借思路** |
| 立场坐标轴可视化 | —— | ❌ 无现成方案 | **必须自研** |
| 中文互联网「标签词」捞取 | —— | ❌ 无现成方案 | **必须自研** |

### 1. 采集层 —— 不要指望一个项目通吃

**先说最重要的一条：采集与分析必须彻底解耦。** 采集层是最脆弱、最容易失效、法律风险最高的一环。所以「大量子」的采集层设计成一个**可插拔的适配器**，而不是硬依赖某个爬虫。核心分析链路只认一个统一的评论 schema，采集从哪来、怎么来、甚至是不是自动来的，都不影响分析。

#### 逐平台现状（2026-09 核实）

| 平台 | 推荐方案 | 许可证 | 难度 | 备注 |
|------|---------|--------|------|------|
| 百度贴吧 | **aiotieba** | 宽松 | 🟢 易 | pip 库，**匿名即可**取帖子+楼中楼评论，最省事 |
| 抖音 | **Douyin_TikTok_Download_API** | **Apache-2.0** | 🔴 难 | 有评论接口 + REST API + MCP + Docker，许可证最干净 |
| 小红书 | **Spider_XHS** | MIT（自述） | 🔴 极难 | 签名本地纯算，不需浏览器；风控最严，有封号案例 |
| 微博 | **weibo-crawler** | —— | 🟡 中 | 评论只在一级，且仅 `sqlite` 模式有效 |
| 知乎 | **ZhihuApis** | —— | 🔴 难 | x-zse-96 动态签名，需 Cookie |
| B站 | 无稳妥开源方案 | —— | ⚠️ **法律风险** | `bilibili-api` 2026-07 收到律师函已关停；`bilibili-API-collect` 已 archived |
| 全平台 | **MediaCrawler** | ⚠️ **NON-COMMERCIAL** | —— | 见下方说明 |

#### MediaCrawler 的正确用法

[NanmiCoder/MediaCrawler](https://github.com/NanmiCoder/MediaCrawler) · 65.8k star · 仍在高频维护（2026-09-19 还在修抖音 ArgusSecurityPlugin 风控）

七平台 × 七能力（含二级评论）全覆盖，技术上确实是唯一一个通吃的。**但有三个坑必须知道**：

1. **许可证是 `NON-COMMERCIAL LEARNING LICENSE 1.1`** —— 不是 GPL，是**明确禁止商业用途、禁止大规模爬取**。个人学习研究可以用，想做成产品卖就不行。
2. **没有库 API**。没有 PyPI 包，没有 SDK，只有 `main.py` 命令行入口。它的 WebUI 也只是 subprocess 包命令行。**工程上不建议 import 它的内部模块。**
3. **评论爬取默认关闭**（`ENABLE_GET_COMMENTS = False`），要手动打开。

**决策**：把 MediaCrawler 当作**参考实现 / 可选 CLI**，而不是生产依赖。「大量子」提供一个适配器读它输出的 JSONL/CSV，用户自己装了就能用；不装也不影响主流程。

#### 「大量子」的采集策略

```
                    ┌──────────────────┐
 粘贴 / 上传文件 ───→ │                  │
 MediaCrawler 产物 ─→ │   统一评论接入层   │ ──→ 清洗去重 ──→ 分析管道
 专用平台适配器  ───→ │  (adapter 可插拔)  │
 任意 CSV 列映射 ───→ │                  │
                    └──────────────────┘
```

内置四种接入方式，按可靠性排序：

1. **粘贴 / 上传**（永远可用，零风险）—— txt / csv / json / jsonl / xlsx
2. **通用 CSV 列映射**（万能兜底）—— 任何爬虫的输出，界面上点选哪列是评论、哪列是点赞，就能导入
3. **MediaCrawler 产物适配器** —— 自动识别它输出的 JSONL/CSV 字段结构
4. **通用命令适配器** —— 界面里填一条命令模板（如 `python main.py --platform tieba ...`），工具负责调用、等它跑完、读产物。这样**接任何新爬虫都不用改代码**。

以及一个界面上必须显示的**风险提示**：每个平台标注许可证与法律风险等级，B站单独警示（两个主力开源库已被律师函关停）。

### 2. BettaFish（微舆）—— 名字很像，但不是你要的东西

[666ghj/BettaFish](https://github.com/666ghj/BettaFish) · star 42.3k · GPL-2.0 · 活跃维护

它的工作流是：`MindSpider 爬虫 → 三 Agent 并行分析 → ForumEngine 多轮辩论 → Report Agent 生成报告`。是一个**舆情研究报告生成器**。

关键判定：**它不含「评论 → 立场类别（带条数占比）」这一环。** 它的 `InsightEngine/tools/sentiment_analyzer.py` 用的是本地 HF 模型做 **5 级情感极性**分类（非常负面/负面/中性/正面/非常正面），输出的是情感分布，不是立场类别 —— 没有 stance、没有观点簇、更不会从评论原文里捞用户自造的标签词。

它的图表类型只有 Chart.js 的 `line/bar/pie/doughnut/radar/polararea/scatter/bubble/horizontalbar`，**没有立场谱系轴**。

**决策**：不复用。它的 `ReportEngine` 的 IR→HTML 报告管线设计可以借鉴，但 GPL-2.0 有传染性，别碰代码。

### 3. Jigsaw sensemaking-tools —— 最接近的「想法」来源

[Jigsaw-Code/sensemaking-tools](https://github.com/Jigsaw-Code/sensemaking-tools) · **Apache-2.0** · Google Jigsaw 出品 · 已停止维护

这是思路质量最高的一份参考资料。它的管道：

```
原始反馈 CSV
  → categorization_runner   话题发现 + 引文抽取（学出「话题 → 观点」两级分类学）
  → get_bridging_scores     对引文打分（推理性/好奇心/个人叙事）
  → generate_report_text    递归摘要：观点 → 话题 → 全局
  → report_ui               交互式可视化
  → propositions + 模拟陪审团  找出能达成广泛共识的命题
```

三个值得偷的关键设计：

1. **两级学出来的分类学**（topic → opinion），而不是预设标签。这正好对应你要的「第一步捞标签 → 第二步语义合并」。
2. **每条归类都挂引文（quote）**。分类结果不是凭空生成的标签，而是绑定了原文的。
3. **模拟陪审团**找共识 —— 用 LLM 扮演不同立场的陪审员给命题打分，找出跨立场都能接受的表述。这是「共识与撕裂点」那一节的正确做法。

**决策**：**不搬代码**（依赖 `google-genai`、`google-cloud-firestore`、`google-cloud-dlp`、`google-cloud-run`，强绑 GCP），但**照搬它的方法论**。它的 `default-additional-context.md` 里的约束「Every claim or consensus statement must be rooted in the provided text」正是我们要的证据链原则。

### 4. Talk to the City —— 同一件事的重型 SaaS 实现

[AIObjectives/tttc-light-js](https://github.com/AIObjectives/tttc-light-js) · Apache-2.0

把评论聚成 `topic → subtopic → claim → quote` 的嵌套树，生成可交互报告。架构是 `next-client + express-server + pipeline-worker`，外部依赖 Firebase / GCS / Redis / Pub-Sub。

**决策**：架构太重，不复用。但它证明了「嵌套树 + 引文」这个呈现形态是可行的。

### 5. 必须自研的部分

调研完之后，真正没人做好的是这三件事 —— 也正是「大量子」的价值所在：

1. **中文互联网的标签词捞取**。「小仙女」「下头男」「普信男」「捞女」这类词是**特定社群自造的流通标签**，学术化的「支持/反对/中立」抓不住它，通用话题建模也抓不住它。这一环必须专门做提示词工程。
2. **立场坐标轴**。系统性检索确认：**没有任何开源项目做过「按对立程度排序的一维立场轴」**。Pol.is 只是无标签的二维 PCA，而且官方明确它的 ML 只跑在「同意/反对/跳过」的投票矩阵上、**根本不能吃自由文本评论**；Talk to the City 是无序语义簇；Jigsaw 不排序；LLooM 和 TopicGPT 也都不排序。前端更是连一个仍在维护的 Likert 组件都没有（D3 的示例 2014 年就停更了）。
3. **端到端的中文一键流程**。从评论导入到立场一览报告，中间不需要人工倒腾 CSV。

### 6. 还值得继续借的几个项目

调研挖出来的、以后扩展时可以借的东西（本次没有采用，但记下来）：

| 项目 | 能借什么 | 许可 |
|------|---------|------|
| [TopicGPT](https://github.com/chtmp223/topicGPT) (NAACL'24) | `refine_topics` 合并近重复；自带 ARI / 纯度 / NMI 评测指标，可以用来量化我们阶段二的质量 | MIT |
| [LLooM](https://github.com/michelle123lam/lloom) (CHI'24) | 与本项目阶段一+二**最同构**的学术工作：概念归纳 + 自然语言纳入标准 + prevalence 占比 | BSD-3 |
| [BERTopic](https://github.com/MaartenGr/BERTopic) | zero-shot 混合归类（把类别名当 `zeroshot_topic_list`）。**规模逃生舱**：将来跑 10 万条以上时用，但向量对「立场对立」不敏感，必须叠加阶段一已抽出的 `stance` 做二次切分 | MIT |
| [C-STANCE](https://github.com/chenyez/C-STANCE) | 48,126 条中文微博立场对，可以用来量化阶段一 stance 四分类的准确率 | 研究用途 |
| [argilla](https://github.com/argilla-io/argilla) | 人工复核层。想验证占比可信度时，抽 200 条做人工标注 | Apache-2.0 |
| [Sensemaker `report_ui`](https://github.com/Jigsaw-Code/sensemaking-tools) | 堆叠占比条 + 环图的可视化，支持 `locale=zh-CN`。若以后想要「占比表」视图可以改造 | Apache-2.0 |

关于阶段二，还有一条**值得写进设计说明的优势**：TopicGPT 需要专门加一轮 `correct_topics` 纠错来抑制标签漂移，
而本项目的做法是「**别名映射表 + 纯 Python 计数**」—— 归类完全确定，从根本上不存在漂移问题。

### 7. 一个必须说清的架构前提：阶段一和阶段二之间没有向量聚类

调研建议过「先嵌入预聚、再让 LLM 簇内合并」，
这确实能降低「模型偷懒合并」的风险，但需要引入嵌入模型（本地跑 bge-m3 要装 torch，
而 DeepSeek 没有 embeddings 接口）。

本项目选择了另一条路：**给每个标签词附上最多 3 条代表性原文**，让模型看着真实用例做合并判断。
只看词面，「捞女」和「物质女」该不该合并很难判断；看了原文就清楚了。

代价是这一级只能一次性喂给模型（超过 1200 个标签词会自动分两轮）。
好处是**零新增依赖**，而且合并结果带 `merge_notes`，有争议的合并会被明确记录在报告里。

如果将来标签词规模涨到需要嵌入预聚，`stage2_canon.py` 的 `build_term_stats` 是唯一需要改的地方。

## 二、核心设计原则

### 原则 1：LLM 只做归纳，绝不做计数

这是整个架构最重要的一条。

大模型数数不准。如果让它「统计每个类别有多少条」，它会给你一个看起来合理但是编的数字。所以：

```
❌ 错误做法：把 500 条评论扔给 LLM，让它输出「类别A：137条，27%」
✅ 正确做法：LLM 只负责给每条评论打上标签 ID，
             计数用 Python 对标签 ID 做 Counter
```

每一类的条数、占比，全部由代码在标签 ID 上算出来。**LLM 的输出里永远不出现条数和百分比。** 这样占比一定是自洽的（加起来等于 100%），也一定能回溯到具体评论。

### 原则 2：标签必须从原文捞，而且必须留证

提示词里硬约束：**只允许使用评论原文中出现的词**，不许发明学术分类。每条标签都要记下：

- `term` —— 评论者自己用的词（原文用词）
- `claim` —— 这个词背后在主张什么（一句话）
- `stance` —— 支持/反对/中立/其他
- `evidence` —— 最能代表它的原文短句（真的从评论里切出来的）
- `comment_id` —— 来自哪条评论

有了 `comment_id`，任何一个类别的占比都能一键下钻到原始评论列表。**这是这个工具和「AI 瞎编一份报告」的根本区别。**

### 原则 3：两段式归约，把成本压到最低

评论可能有几万条，但**不同的标签词只有几百到几千个**。所以分两级：

```
第一级（贵，可并发）  10,000 条评论  →  每条评论的标签词    [LLM, 分批并发]
第二级（便宜，一次）   ~800 个不同标签 →  ~15 个立场类别      [LLM, 单次调用]
第三级（免费，确定性） 用别名映射表把评论归到大类             [纯 Python]
```

第一级的输出是「评论 → 标签词」的映射（数据量大但每条很短）；第二级只需要把**去重后的标签词清单**喂给模型，输入量小一个数量级。

### 原则 4：DeepSeek 的成本结构决定了两个关键设置

**（一）思考模式必须按阶段显式开关。**

DeepSeek **默认打开思考模式，且 effort 默认为 `high`**。这在本项目里是个陷阱：

- 阶段一要处理几千条评论，是最机械的批量抽取任务。开着思考模式，模型会先吐一大段
  思维链，而这些 token **按输出价计费** —— flash 空闲时段输出 4 元/M，
  而输入未命中才 1 元/M。**输出是最贵的一环，思维链纯属浪费。**
- 官方文档还明确：**思考模式下 `temperature` 静默失效**（传了不报错但也不生效）。

所以阶段一、二显式传 `{"thinking": {"type": "disabled"}}`，
只在真正需要判断的阶段保留（陪审团和报告用 `high`，合并和坐标轴用 `low`）。
代码里 `THINKING_BY_STAGE` 是唯一的开关表。

**（二）提示词按「稳定前缀 + 变化后缀」组织，但缓存没那么好拿。**

缓存命中输入价 0.02 元/M，未命中 1 元/M —— 差 50 倍。所以所有批次共用的那一大段
system 提示词放在最前面且逐字不变，变化的评论数据放最后。

但官方规则是「**完整匹配缓存前缀单元**」才命中，而且公共前缀要等系统检测到之后才落盘。
按官方例二：**前两次请求都不命中，第三次才开始命中。**

推论（反直觉但真实）：**并发数 ≥ 批次数时，一批都命中不了缓存**，
因为它们几乎同时发出，前序请求还没结束、缓存还没落盘。
只有批次数超过并发数之后，后面的波次才开始命中。

工具的成本预估按这个模型算，并会明确告诉你「本次有一批都命中不了」还是
「前 N 批无缓存，之后 M 批会命中」。

空闲时段（工作日 9-12、14-18 之外，以及周末和法定节假日全天）价格再减半。

### 原则 5：抽样必须随机，而且必须披露

评论上万时全量跑又慢又贵，抽样是必要的。但抽样方式决定了结论是否可信：

- **按热度取 TOP N 是错的**。高赞评论偏向主流立场，会把小众立场系统性地抹掉 ——
  而「看清所有立场」恰恰是这个工具的目的。所以用**均匀随机抽样**。
- **固定随机种子**。同样的输入和上限，重跑抽到同一批，结果可复现。
- **抽样比例写进报告**。占比的分母是抽样后的条数，这件事读者必须知道。

`sample_comments()` 返回的说明会一路流到 `stats.extra["sampling"]`，
再进报告提示词。

### 原则 6：每阶段产物落盘，可断点续跑

跑一次 5000 条评论要花真金白银。所以每一阶段的中间产物都写成 JSON 存到 `data/runs/<run_id>/`：

```
data/runs/20260101-120000-某事件/
├── 00_input.json       清洗去重后的评论
├── 01_labels.json      逐条捞取的标签（最贵的一步，跑完就存着）
├── 02_canonical.json   合并后的立场类别 + 别名映射表
├── 03_stats.json       确定性统计出的条数与占比
├── 04_axis.json        坐标轴排布
└── 05_report.json      最终报告
```

改了提示词想重跑第二步？只重跑第二步，第一步的结果直接复用，不重复花钱。

## 三、五阶段流水线

```
                  ┌─────────────────────────────────────────┐
输入               │ ① 捞标签   ② 合并      ③ 计数    ④ 坐标轴  ⑤ 报告 │
                  └─────────────────────────────────────────┘

粘贴/上传/爬取
   ↓
[清洗去重]  去广告、去纯表情、去重复、保留点赞数
   ↓
评论列表 ──→ ① 逐条捞标签
              LLM 并发分批，每批 N 条
              输出：comment_id → [{term, claim, stance, evidence}]
              ★ 这个阶段最贵，产物落盘
   ↓
标签词清单 ─→ ② 语义合并
              去重后的标签词 + 每个词的代表性证据
              LLM 单次调用，学出「立场类别」
              输出：[{canonical, aliases[], core_logic, pole}]
              ★ 这一步决定最终质量
   ↓
别名映射表 ─→ ③ 确定性归属与统计
              纯 Python：Counter，无 LLM
              加权（可选）：按点赞数加权 vs 按条数
              输出：[{canonical, count, pct, evidence[]}]
   ↓
类别列表 ──→ ④ 坐标轴排布
              LLM 判断两极是什么，把类别排到 0~1 谱系上
              输出：{left_pole, right_pole, positions[]}
              ★ 这就是「混乱粉笔」的坐标轴
   ↓
全部 ─────→ ⑤ 生成报告
              混乱粉笔式结构：标题 / 背景 / 坐标轴 / 各立场详解 / 共识与撕裂点
              ★ 共识与撕裂点用「模拟陪审团」找，不用模型瞎猜
```

### ① 捞标签（stage1）

- 输入：清洗后的评论，分批（默认每批 200 条，可调）
- 并发：DeepSeek flash 并发上限 2500，实际按 8~16 并发跑，避免触发风控
- 输出格式：JSON Output（`response_format={'type':'json_object'}`）
- 关键提示词约束：
  - 「**只使用评论原文中出现的词**作为标签，不要发明学术分类」
  - 「不要笼统地说支持/反对，要具体到评论者用的那个词」
  - 「一条评论有多个立场就拆成多条」
- 失败处理：单条解析失败重试；整批失败降级为拆半重试

### ② 语义合并（stage2）

这是「大量子」的灵魂一步。输入不是评论，是**去重后的标签词清单**：

```
续航拉胯 (312次)
电池不行 (287次)
半天就没电 (98次)
...
```

让 LLM 把它们合并成 `续航问题`，并记下别名。同时判断每个类别的 `pole`（它站在争论的哪一边）。

合并质量的关键：**给每个标签词附上最多 3 条代表性原文**。只看词面，「捞女」和「物质女」该不该合并很难判断；看了原文就知道。

### ③ 计数（stage3）

纯 Python。核心是一个 `alias → canonical` 的字典：

```python
counter = Counter()
for comment in comments:
    for label in label_map.get(comment.id, []):
        canonical = alias_to_canonical.get(label.term)
        if canonical:
            counter[canonical] += 1
```

产出：条数、占比（保留一位小数）、按点赞加权占比、每个类别下的代表原文 TOP N。

同时输出**未归类比例** —— 如果大量评论没匹配上，说明第二步合并漏了，工具会警告。

### ④ 坐标轴（stage4）

这是「混乱粉笔」那套呈现的核心，也是**所有现成开源工具都没有的一环** ——
它们只有饼图、柱状图和嵌套树；连一个仍在维护的 likert 组件都找不到。
所以这块完全自研，前端手写 SVG。

关键设计：**模型只判断两极和贴合度，位置由代码算。**

```
模型输出： {"canonical": "隐私权优先", "left_affinity": 8, "right_affinity": 94}
代码计算： x = right / (left + right) = 94 / 102 = 0.922
```

为什么不让模型直接给 `x`：

1. **数值不可复现**。同一个输入，两次跑出来的位置可能不一样。
2. **会逼模型制造对立**。第一版提示词里写了「别把类别都挤在 0.45~0.55」——
   这等于要求模型凭空拉开区分度，产出的可能是不存在的对立。
   现在改成明确告诉它「挤在一起是真实情况的反映，不是错误」。
3. **无法追溯**。现在两个贴合度分数会一并落盘，轴位随时可以复算和核对。

输出结构：

```json
{
  "axis": {"name": "...", "left_pole": "...", "right_pole": "...", "note": "..."},
  "alignments": [
    {"canonical": "隐私权优先", "left_affinity": 8, "right_affinity": 94}
  ]
}
```

模型漏掉的类别、或整体调用失败时，降级为「按 pole 分组、组内按占比排开、均匀铺在轴上」，
保证界面永远能用，并且在界面上明确标注这是降级结果。

### ⑤ 报告（stage5）

按「混乱粉笔」的结构生成：

1. **标题** —— `《XX事件全部立场一览：A、B、C……丨X坐标轴》`
2. **事件背景** —— 两三句话说清在争什么
3. **立场坐标轴** —— 谱系 + 占比
4. **各立场详解** —— 每个类别：标签词 / 核心逻辑 / 典型原文 / 占比
5. **共识与撕裂点** —— 用模拟陪审团法：让 LLM 扮演每个立场的持有者，对若干命题打分，找出跨立场高分的（共识）和两极分化的（撕裂点）
6. **理论锚点**（可选）—— 关联学术概念

## 四、技术栈

选型原则：**零新增依赖，不引入构建步骤。**

| 层 | 选型 | 理由 |
|---|---|---|
| 后端 | **Flask 3.1**（本机已装） | 本机已有，不引入 FastAPI/uvicorn |
| HTTP | **httpx 0.28**（本机已装） | 直接打 DeepSeek 的 OpenAI 兼容 REST，不装 openai SDK |
| 数据模型 | **pydantic 2.13**（本机已装） | 结构化校验 |
| 表格 | **pandas 3.0**（本机已装） | 读 csv/xlsx |
| 中文分词 | **jieba 0.42**（本机已装） | 清洗阶段做粗去重，不参与主流程 |
| 前端 | **原生 HTML + CSS + JS** | 无 npm、无构建，双击即用 |
| 坐标轴 | **手写 SVG** | 谱系轴没有现成库，手写反而更可控 |
| 存储 | **JSON 文件** | 无需数据库 |

**没有新增依赖** —— 这点很重要，装不上依赖是本地工具最常见的死法。

前端不引 CDN。图表、样式、字体全部本地化，断网也能用。

## 六、成本估算

以 5000 条评论为例，用 `deepseek-flash` 空闲时段价格：

| 阶段 | 输入 tokens | 输出 tokens | 说明 |
|---|---|---|---|
| ① 捞标签 | ~1.5M（首次） | ~0.5M | 分批 200 条，后续批次命中缓存 |
| ② 合并 | ~0.15M | ~0.03M | 只喂去重后的标签词 |
| ④ 坐标轴 | ~0.02M | ~0.01M | 单次 |
| ⑤ 报告 | ~0.1M | ~0.05M | 递归摘要 |
| **合计** | **~1.8M** | **~0.6M** | |

- 缓存命中把①的输入成本从 1 元/M 压到 0.02 元/M
- 空闲时段再打五折
- **估算总成本：约 2~4 元人民币 / 5000 条评论**

工具会在每次运行前显示预估成本，运行后显示实际花费。高峰时段会提示「建议等到空闲时段再跑，能省一半」。

## 七、已知的坑

以下每一条都是实际踩到或预判到的，都已加了对策。

### 提示词与模型行为

1. **DeepSeek JSON Output 有概率返回空 content**（官方文档明确承认）。
   对策：空响应走重试；整批失败降级为拆半重试。
2. **模型会「偷懒合并」**。给它 200 条评论，它可能只输出 30 条标签然后说「其余类似」。
   对策：提示词强制「必须逐条输出，id 必须与输入一一对应」，
   并且在代码里校验**输出 ID 集合 == 输入 ID 集合**，缺了的单独小批补跑。
3. **模型会「发明」分类**。不约束的话它很乐意输出「性别平权意识觉醒」这种学术腔。
   对策：提示词里写死「只允许使用评论原文中出现的词」，并给了正反例。
4. **中文的「同词反用」**。「女权」和「女拳」读音相同、立场相反；
   「小仙女」既可能是自称也可能是贬称。系统性地合并它们会把对立的两派揉成一类。
   对策：阶段二提示词里点名这条铁律，并要求有争议的合并写进 `merge_notes`。

### 管道健壮性

5. **阶段一整体失败后会静默穿过空阶段**。`asyncio.gather(return_exceptions=True)`
   把每批的异常都吞掉了，于是空标签一路流到阶段五，最后在生成报告时才炸，
   用户看到的是一个莫名其妙的晚期错误。
   对策：加「失败快速上报」——捞不到任何标签立刻停下，并说清排查方向（Key？余额？网络？）。
6. **阶段二返回非法 JSON**。对策：同样快速上报，而不是带着空立场继续往下跑。
7. **失败的运行也已经花了钱**。对策：错误信息里带上本次已消耗金额，
   并说明已完成的阶段产物已保留、重跑会复用。
8. **`stats` 落盘早于坐标轴**，导致读回来时 `x` 丢了。
   对策：坐标轴跑完补存一次 stats；API 读旧数据时再从 `04_axis.json` 合并回去。

### 呈现与统计

9. **占比的两种口径**。按「评论条数」和按「点赞数加权」会得出很不一样的结论
   （一条 10 万赞的评论和一条 0 赞的评论，代表性差了几个数量级）。
   对策：**两个都算、并排显示**，不替用户做选择。
10. **一条评论多个立场导致占比之和 > 100%**。
    对策：同时提供「构成占比」（所有标签归属里的份额，加起来正好 100%），
    并在报告里强制声明这件事，避免读者误读。
11. **未归类评论被默默排除**会让占比虚高。
    对策：报告必须声明分母：「本次分析基于 N 条，其中 X 条没有归入任何立场」。
12. **同一条评论重复同一个词会刷权重**。对策：一条评论对同一个类别只计一次。
13. **坐标轴在窄屏下被等比缩到不可读**。第一版用固定 `viewBox 1000` +
    `width:100%`，容器 600px 时 12px 的字缩成 7px。
    对策：改成按容器实际像素宽度 **1:1 建立坐标系**，标签用贪心算法分配泳道和行号避让；
    容器尺寸变化时用 `ResizeObserver` 重画。

### DeepSeek 接口的真实坑（都是打真实接口才发现的）

14. **思考模式默认是开的，且 effort=high**。几千条评论的机械抽取任务开着它，
    思维链 token 按输出价计费（比输入贵 4 倍），成本会翻好几倍；
    而且思考模式下 `temperature` 会**静默失效**。
    对策：按阶段显式传 `thinking`（见「原则 4」），机械阶段关掉。
15. **缓存不是「第一次之后就一直命中」**。官方规则是完整匹配缓存前缀单元，
    前两次请求都不命中；而并发 ≥ 批次数时因为是同时发出，**一批都命中不了**。
    对策：成本预估按这个模型算，并把结论如实告诉用户，不做乐观假设。
16. **JSON Output 要求提示词里必须出现 `json` 字样**，否则接口会报错。
    对策：加了一条测试，逐个检查四个 JSON 阶段的提示词都含这个关键字。
17. **`max_tokens` 在思考模式下会被思维链吃掉**。给陪审团和报告这些开着思考的
    阶段留了更大余量（24576 / 32768）。`max_tokens` 调大不会多花钱，只按实际输出计费。

### 接口侧的真实坑（都是打真实接口才发现的）

18. **思考模式和输出正文抢同一份 `max_tokens` 预算。**
    阶段二要把几百条观点短句**原样回抄**进 `aliases`，输出本来就长。
    开着思考模式（哪怕只是 `low`）时，思维链会先把整个预算吃光 ——
    返回 `finish_reason=length` 而正文一个字都没有。
    **更坑的是拆小输入没用**：每一份照样被吃光。
    对策：凡是「输出里要大量回抄输入」的步骤，一律关掉思考模式。
    判定标准写在 `THINKING_BY_STAGE` 的注释里。

19. **被 `max_tokens` 截断的 JSON，重试是没有意义的。**
    同样的输入、同样的预算，只会再截断一次，然后你会拿到一个
    读不懂的 `JSONDecodeError`。对策：单独立一个 `TruncatedError`，
    把它和「偶发网络失败」区分开，让调用方拆小输入而不是傻重试。

20. **让模型「原样回抄类别名」是不可靠的映射方式。**
    压缩类别时如果让模型把被合并的**类别名**列进 `aliases`，
    名字只要差一个字，`别名→类别` 的映射就断了，那一整片观点会掉进兜底桶
    （实测兜底桶因此从 1.6% 反弹到 18%）。
    对策：改成**按编号合并**（`members: [1,3,7]`），纯机械映射，
    而且可以程序化校验覆盖度 —— 从根上不可能丢。

21. **只喂去重观点时模型会过度拆分。**
    936 个观点被拆成 32 个类别，其中「批评男版形象缺乏辨识度」和
    「批评男版形象是小圈子产物」本该是一类。一份立场一览有三十多条没人读。
    对策：加一道**最终压缩**。只喂类别（几十条），很便宜，压到 16 个以内。

22. **顺手记一条 Command Code 的接入结论**（本项目最终没用它，但值得留下）：
    它的 provider 插件里写了**两条路** —— `{base}/alpha/generate` 给 CLI 用，
    `{base}/provider/v1/chat/completions` 给 Provider 档的 API 用。
    **Go 档只能走前者，而前者明确禁止被当代理调用**（官方原文：
    "Proxy use detected. This endpoint only serves CLI... violates the TOS
    and will result in account ban"）。
    所以要程序化批量调用，**必须升级到 Provider 档**，别去碰 `/alpha/generate`。

### 数据与合规

18. **采集的风控与法律风险**。MediaCrawler 虽然用 CDP 模式降低风险，
    但高频抓取仍可能触发平台限制；B站两个主力开源库已被律师函关停。
    对策：**采集与解析完全解耦** —— 采集挂了不影响已经存下来的数据继续分析；
    界面上标注各平台的许可证与风险等级。
19. **样本代表性**。热门评论 ≠ 全部评论。
    对策：明确显示「本次分析基于 N 条评论」，并在报告里写明，
    不让用户误以为这是全量民意。
20. **清洗会改变分母**。去掉广告、灌水和重复之后，
    `pct` 的分母是「有效评论数」而不是「原始抓取数」。
    对策：清洗明细（去空/去太短/去灌水/去广告/去重复/保留）在导入预览和报告里都完整展示，
    用户随时能看到丢掉了什么。
