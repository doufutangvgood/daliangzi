# 「大量子」能力复刻 · 开源方案调研报告

> 调研目标：把某网络事件下的成千上万条评论，自动归纳成几个**立场类别**，每类带条数/占比，并呈现为**立场坐标轴 / 立场一览表**（不预设标签，从评论原文"捞取"用户自用标签词，再合并聚类）。
> 调研方式：`web_search` + `web_fetch`，逐个核对 GitHub API 元数据、README 与源码文件。
> 所有事实均附来源 URL；标注「✅实测核对」的为直接读取了源码/元数据。

---

## 0. 结论速览

1. **没有任何一个开源项目可以直接产出你要的"大量子"。** 不存在"输入事件 → 输出立场类别+占比+坐标轴"的开箱即用项目。
2. 但存在一条**高复用度的拼装路线**，能把自研工作量从"重造整条链路"压缩到"只写一个立场轴排序 + 一层适配"：
   - **归类引擎（LLM 归纳类别 + 归类 + 给理由）** → TopicGPT / LLooM 的提示词与流程可直接抄；
   - **聚类引擎（向量聚类做分组）** → BERTopic 原生支持"预设类别名 + 向量相似度归类 + 剩余自动聚类"的混合模式；
   - **前端呈现（类别占比 + 引用原文）** → Jigsaw Sensemaker 的 `report_ui` 是一个**独立可喂数据的前端**，输入只要一个 `opinions.csv`；
   - **谱系图（ordered stance band）** → Vega-Lite 官方有 diverging stacked bar（Likert）现成规格；
   - **立场轴排序** → 这一步**没有现成组件，必须自研**（可用 PCA / semantic projection 作参考实现）。
3. **「微舆 BettaFish」不是答案**：它是"爬虫 → 多 Agent 舆情研究 → 报告生成"，不含"评论观点聚类成带占比的类别"这一环；它只有 5 级**情感极性**分布。详见第 1 节。
4. 与你需求最接近的三个项目是 **Sensemaker（Jigsaw）**、**LLooM（Stanford CHI'24）**、**Talk to the City**——三者都做"开放文本 → 归纳出人类可读的类别/观点"，但都不产出"对立程度排序的坐标轴"。
5. **Pol.is 看似最像"立场坐标轴"，但不能用**：官方明确其机器学习**只跑在"同意/反对/跳过"投票矩阵上，因此是语言无关的**，无法直接吃非结构化评论。它的数学管线可用 **Red Dwarf**（MPL-2.0，Python 库）复用，但依然需要投票矩阵。
6. **许可陷阱**：Pol.is、Consider.it、Harmonica 是 **AGPL-3.0**（自托管对外服务会触发网络 copyleft）；BettaFish 是 **GPL-2.0 且明确禁商用**；MediaCrawler 亦禁商用。相对安全的组合是 **Apache-2.0（Sensemaker / TttC）+ MIT（BERTopic / TopicGPT / KeyBERT / FlagEmbedding）+ BSD-3（LLooM / Vega-Lite）+ MPL-2.0（Red Dwarf）**。

### 1.2 技术栈 ✅实测核对

纯 Python 模块化，**不依赖 LangChain / LlamaIndex 等框架**（README 明确"从0实现，不依赖任何框架"）：

- 单 Agent 调试：Streamlit（三个独立 app，:8501/8502/8503）
- 数据库：PostgreSQL（推荐）或 MySQL（README 快速开始）

### 1.3 完整工作流（爬虫 → 分析 → 报告）✅实测核对（README）

```
MindSpider 爬虫系统
  ├─ BroadTopicExtraction   今日新闻 → 热点话题/关键词提取
  └─ DeepSentimentCrawling  深度舆情爬取（内嵌 MediaCrawler）
        ↓ 写入 PostgreSQL
三个分析 Agent 并行
  ├─ QueryEngine    国内外新闻广度搜索
  ├─ MediaEngine    多模态（图/短视频）理解
  └─ InsightEngine  私有舆情数据库挖掘（含情感分析中间件）
        ↓
ForumEngine「论坛」机制：主持人 LLM 多轮引导 Agent 辩论 + 反思
        ↓
ReportEngine：模板选择 → 布局 → 篇幅规划 → 章节生成 → 装订为 IR
        ↓

```

- 一次完整运行的 7 个阶段表格见 README「一次完整分析流程」。
- 评论抓取量配置：`InsightEngine/utils/config.py` 的 `default_get_comments_limit = 500`（README）。

### 1.4 关键判定：**不含**"评论观点聚类成带占比的类别"

这一条是我逐个文件读代码确认的，不是靠 README 推测：

**证据 A — 情感分析只有"极性"，没有"立场/观点类别"**
`InsightEngine/tools/sentiment_analyzer.py`（✅实测读取）：
- 模型：本地 HuggingFace 模型 `tabularisai/multilingual-sentiment-analysis`（22 种语言）
- 输出：**5 级情感极性** —— `非常负面 / 负面 / 中性 / 正面 / 非常正面`
- 产出结构：`sentiment_distribution`（各类计数）+ `summary`（形如"主要情感倾向为'负面'(X条，占 Y%)"）
- 结论：这是**情感极性分布**。没有 stance（支持/反对）、没有观点簇、没有从评论原文抽取用户自用标签词。

**证据 B — 报告图表类型里没有"立场轴/谱系图"**
`ReportEngine/utils/chart_validator.py`（✅实测读取）支持的 `SUPPORTED_CHART_TYPES` 仅：
`line / bar / pie / doughnut / radar / polararea / scatter / bubble / horizontalbar`（Chart.js）。
即：能用 bar/pie 表达"占比"，但**没有** diverging stacked bar、没有坐标轴、没有立场谱系图。

**结论**：BettaFish 的可复用段是〔爬虫 + 多 Agent 分析 + 报告渲染管线〕；你要的核心〔评论 → 立场类别（带条数占比）→ 立场谱系图〕**必须自研**。

### 3.2 两条路线的优劣

**路线 A：让 LLM 直接归纳类别（把评论喂给 LLM，让它自己给出类别并归类）**

| 优点 | 缺点 |
| :--- | :--- |
| 类别名是**人话**，直接就是"立场名"，不需要人工命名 | **成本随评论数线性增长**（每条评论都要过一次 LLM） |
| 能理解反讽、黑话、圈层梗，中文网络评论优势明显 | **标签漂移**：不同批次/不同调用给出不同类别名，难以稳定 |
| 天然能给"理由/依据引语"（grounding） | **不可复现**：同一批数据两次跑出不同类目数与占比 |
| 能实现你要的"不预设标签、从原文捞标签词" | 类别数不可控（易碎成几十个长尾类） |
| 无需训练 | 上下文长度限制 → 必须分批，**跨批次的类别无法对齐** |

**路线 B：向量聚类做分组 + LLM 只做命名（先嵌入→UMAP→HDBSCAN→对每簇用 LLM 起名）**

| 优点 | 缺点 |
| :--- | :--- |
| **成本与评论数脱钩**：LLM 只需对每个簇调用一次 | 聚类结果只有关键词，**类别名需要 LLM 二次加工** |
| **可复现**：同一向量+同一参数结果稳定 | 密度聚类会把大量评论丢进离群点（噪声），需要额外处理 |
| 占比天然来自簇大小；聚类数可控 | 向量空间里的"近"≠立场上的"同"，可能把"支持 A"和"反对 A"聚到一起（**对立语义在嵌入空间很近**）|
| 排序/坐标轴可由簇心几何量算出 | HDBSCAN 参数敏感，中文短评论（几个字）向量质量差 |

**结论：单用任一条都不够。你需要的类别是"立场"而不是"话题"，而嵌入相似度对"立场对立"是不敏感的（"我支持他"与"我反对他"向量极近）。这正是"混乱粉笔"先捞标签词、再合并的原因。**

### 3.3 已有的"两者结合"成熟方案（重点）

1. **BERTopic + LLM 命名（最成熟、最有性价比）** ✅实测官方文档
   - `bertopic.representation.OpenAI / TextGeneration / LlamaCPP / Ollama / LiteLLM / LangChain / Cohere`
   - 机制：先用 c-TF-IDF 选出**每簇的关键词 + 最多 4 篇最具代表性文档**（`nr_docs`、`diversity`、`doc_length` 可调），只把这些喂给 LLM 生成标签/摘要。
   - **关键收益：LLM 调用量 = O(类别数)，而不是 O(评论数)。**
   - https://maartengr.github.io/BERTopic/getting_started/representation/llm.html

2. **BERTopic zero-shot 模式 = 你要的"预设类别名 + 向量归类 + 兜底聚类"混合** ✅实测官方文档
   - `zeroshot_topic_list`（把类别名嵌入）+ `zeroshot_min_similarity`（余弦阈值）；未匹配的文档走常规聚类流程自动发现新类别。
   - 三种情形：既有预设类又有新发现类 / 全落在预设类 / 全无匹配则退化为普通 BERTopic。
   - https://maartengr.github.io/BERTopic/getting_started/zeroshot/zeroshot.html

3. **BERTopic 软分配（拿"占比"）** ✅实测官方文档
   - `approximate_distribution(docs)` 返回 `n×m` 的 文档×主题 概率矩阵（滑窗 token-set 与各主题的 c-TF-IDF 相似度求和），可用 `visualize_distribution` 画单文档主题分布。
   - https://maartengr.github.io/BERTopic/getting_started/distribution/distribution.html
   - 注意：BERTopic 默认硬聚类（每文档一个主题），HDBSCAN 会产生 `-1` 离群类。

4. **KeyLLM 的"先聚类、每簇只抽一次关键词"** — 官方博客明确该策略："we only extract keywords from 1 document in each cluster and assign the keywords to all documents in the same cluster. This is much more efficient and also quite flexible."
   - https://www.maartengrootendorst.com/blog/keyllm/ 、https://maartengr.github.io/KeyBERT/guides/keyllm.html

5. **TopicGPT 的"生成 → 合并相似 → 删低频 → 归类"**（见 4.1）——这就是"合并聚类"的现成流程。
6. **LLooM 的 Concept Induction**——用 LLM 归纳概念 + 自然语言纳入标准，再回标全量文档（见 4.2）。
7. **BERTopic guided / seeded 模式（半监督微调类别）** ✅实测官方文档
   - `seed_topic_list=[["关键词1","关键词2",...], ...]`：用种子关键词"推"主题，机制是半监督 UMAP + 对种子词施加 **×1.2 的 IDF 权重**。
   - 官方明确这只是"nudge"：若种子主题在数据里不存在或被打散，**就不会被建模出来**。
   - https://maartengr.github.io/BERTopic/getting_started/guided/guided.html
8. **llm-cluster（simonw，Apache-2.0，82★）** —— `llm cluster <collection> <n> --summary`：先算簇，再用第二次 LLM 调用给每簇生成名字+摘要。**已停更但代码极小，是最干净的参考实现**：https://github.com/simonw/llm-cluster
9. **k-LLMmeans（arXiv 2502.09667）** —— 用 LLM 生成的文本摘要**替代数值质心**，仍在嵌入空间做 k-means 分配 → 类别原型可读可审计；且提供确定性的 `k-NLPmeans` 离线版本：https://github.com/jairoadiazr/k-LLMmeans
10. **ClusterLLM**——用 LLM 反馈迭代改进聚类（含"用两两比较预测最优簇数"模块），但**已停更且无 LICENSE**，仅作思路参考：https://github.com/zhang-yu-wei/ClusterLLM

### 3.4 ⚠️ 中文场景的实操陷阱（这一节很重要，直接决定成败）

这一节的事实来自 BERTopic 官方 FAQ 与离群点文档（子调研员核对）：

| 陷阱 | 事实 | 后果与对策 |
| :--- | :--- | :--- |
| **中文分词** | 官方 FAQ 原文："Currently, `CountVectorizer` tokenizes text by splitting whitespace which does not work for Chinese." | **c-TF-IDF 关键词抽取对中文直接失效**（整句被当成一个 token）。必须换自定义 `CountVectorizer` + **jieba**（`jieba.lcut`）。注意：**嵌入向量本身没问题，坏的是关键词那一步**。来源：https://maartengr.github.io/BERTopic/faq.html |
| **UMAP 随机性** | 官方 FAQ 原文："Due to the stochastic nature of UMAP, the results from BERTopic might differ even if you run the same code multiple times." | **两次跑出不同类别数/占比**。必须固定 `random_state`（官方说明会带来一定性能代价）。这是"可复现性"的关键动作 |
| **`-1` 离群点与占比分母** | HDBSCAN/DBSCAN/OPTICS 会把文档标为 `-1` 并从主题表示中排除；官方给出 4 种离群点归并策略（`probabilities`、`distributions`、`c-tf-idf`、`embeddings`），但**明确警告强行归并"might force outliers to be put into topics where they do not belong"** | **你的"占比"分母必须显式声明**（是否含 `-1`）。若忽略 `-1`，百分比是在一个未说明的子集上算的。来源：https://maartengr.github.io/BERTopic/getting_started/outlier_reduction/outlier_reduction.html |
| **`calculate_probabilities` 很贵** | 官方文档指出该参数开销大，只在"少于几十万文档"时比较从容 | 你的量级（10⁴–10⁵）可行，但**除非要用 `probabilities` 归并策略，否则关掉** |

### 5.4 缺口分析：排序轴是本项目唯一的"无人做过"环节

**明确结论（经系统性检索）**：**没有任何开源项目能把"聚类后的文本"渲染成一条按对立程度排序的一维立场谱系。** 现有两大家族都不做这件事：
- (a) **投票 → 二维意见地图 + 群体**（Pol.is 家族）；
- (b) **文本 → 二维簇 / 论证地图，无排序**（Talk to the City、Jigsaw、Democrai argument map）。

| 你的需求 | 现成可复用？ | 缺什么 |
| :--- | :--- | :--- |
| 群体 + 人数 + 占比 | **有投票矩阵就有**（Pol.is `participants-votes.csv` 含 `Group ID`，`group-clusters` 含计数） | 纯文本场景：自己定义"群 = 簇"并计数 |
| **一维有序对立轴** | **完全没有** | Pol.is 是无标签二维 PCA；TttC 是无序语义簇；Jigsaw 无排序 → **必须自算** |
| 带占比的谱系条 | **部分有** | Vega-Lite 发散堆叠柱 recipe 可直接用；数据整形、中立带惯例、轴标签要自己定 |
| **"立场一览表"** | **没有打包组件** | 最接近的都是定制品（Pol.is 后台评论表、Jigsaw `report_ui` 表格） |

**计算排序轴的三条路线：**

1. **投票矩阵第一主成分**：原理清晰、可复现，`red-dwarf` 已直接实现。**前提是你能拿到投票/打分**（纯评论场景需先让 LLM 为每条评论在预设轴上打分）。
2. **LLM 在预声明轴上的立场打分**：最适合纯文本。先声明一条轴（如 −100…+100），让 LLM 为每条评论/每个类别打分，再按分排序。**必须做轴定义 + 人工验证**，否则得到的是"LLM 的轴"而不是"网民的轴"。
3. **两两对立比较 → MDS / 序数嵌入**：最贴合"按对立程度排序"的字面需求（LLM 只回答"A 与 B 有多对立"这类成对判断题），但**最贵、最不确定**。

**可直接借鉴的投影算法：**

- **Semantic Projection（语义投影）**：把向量投影到"由两个对极陈述定义的语义轴"上，得到标量排序分。
  - 论文（Nature Human Behaviour 2022）：https://www.nature.com/articles/s41562-022-01316-8
  - 参考实现：https://github.com/esfahany/semantic-projection （8★，notebook 实现投影与排序）
- **Anchor 法**（semantic projection 的简化版）：手工定义两个极点陈述，对每个类别算与两极的相似度差 → 投影到 [-1, 1]。
- **簇心 PCA**：对类别中心向量做 PCA，取第一主成分作主轴（Pol.is 处理参与者用的是同一思路）。

| 2 | **标签归并（同义/近义/上下位合并）** | TopicGPT 的 `refine_topics` 只做"近重复合并 + 删低频"，不做"立场归并"；没有面向中文网络用语的可直接用的归并器 | 嵌入相似度预聚类 + LLM 判定合并；保留"合并映射表"以便审计（这是可复现性的关键） |
| 3 | **立场轴排序（坐标轴的核心）** | **没有任何开源方案把"多个立场"排到一条对立程度轴上**（已系统检索确认）。Pol.is 只做无标签二维 PCA 且依赖投票矩阵、不能吃自由文本；TttC 是无序语义簇；LLooM/TopicGPT 都不排序 | 三条路线：① 第一主成分（**参考实现 Red Dwarf**，MPL-2.0）；② LLM 在预声明轴上打分；③ 两两对立比较 → MDS/序数嵌入。投影算法可抄 semantic-projection / Anchor 法 |
| 4 | **稳定聚类 + 占比统计** | 占比可由簇大小得到，但**"立场对立"在嵌入空间是近邻**（"支持 X" 与 "反对 X" 向量极近），纯向量聚类会把对立立场合并 | 两步走：先按"话题/对象"聚类，再在每个簇内按"立场极性"二分/多分；用 zero-shot 模式把已知类别钉住 |
| 5 | **跨批次/跨事件的类别对齐与可复现性** | LLM 归纳必然产生标签漂移；开源项目都没有解决"两次跑出不同类目"的问题 | 固定 codebook + 版本化提示词 + 缓存 + 种子温度 0 + 让 LLM 只做"分配"不做"发明"；引用 arXiv 2511.14528 的质控建议（人工监督、审计追踪） |
| 6 | **中文场景的提示词本地化与反讽/黑话鲁棒性** | Sensemaker/stance-llm 的提示词是英文导向；中文网络反讽是 LLM 立场判断的主要失败点 | 用 C-STANCE/微博立场数据集做评测集，量化不同提示词方案的中文准确率（参考 arXiv 2309.13734 的对比方法） |
| 7 | **立场谱系图的前端组件** | Vega-Lite 只给"diverging stacked bar"图元；把"类别→轴上位置→宽度"这套数据契约画出来，需要自己组装 | 直接采用 Vega-Lite 规格，自己产出 `{类别, 轴上位置, 人数, 占比, 极性}` 数据 |
| 8 | **"立场一览表"的交互与溯源** | 没有现成 UI 同时给"类别名 + 占比 + 代表引语 + 理由"，除了 Sensemaker 的 report_ui（但它不排序、不中文优化） | 以 Sensemaker `report_ui` 为基线改造，或自建（D3 + 你已有的引语字段） |
| 9 | **合规与法律边界** | 爬虫合法性、平台条款、数据用途——没有任何开源许可帮你解决 | 用 MediaCrawler 需自行评估；BettaFish 为 GPL-2.0 且声明禁商用 |

## 8. 针对「大量子」的推荐技术组合

### 8.1 推荐流水线（以"能落地 + 成本可控 + 可复现"为目标）

```
① 采集      MediaCrawler（B站等，含二级评论）→ 落库
   ↓        复用；无需自研

② 清洗/切分 去重、去广告、去 @、保留原文与用户自用标签词/话题标签
   ↓        轻量自研

③ 标签抽取  LLM 按 JSON Schema 抽取：{comment_id, 自用标签词[], 立场对象, 极性, 理由, 原文引语}
   ↓        提示词参考 TopicGPT/LLooM；可靠性用 Instructor 或 vLLM+Outlines 保证
   ↓        （LangExtract 若需要"指回原文位置"的溯源）

④ 归并聚类  嵌入(bge-m3 等中文强向量) → 相似度预聚 → LLM 判定同义/上下位合并 → codebook v1
   ↓        参考 TopicGPT.refine_topics；保留合并映射表
   ↓        ⚠️ 中文必须换 jieba 分词的自定义 CountVectorizer；UMAP 固定 random_state

⑤ 归类+占比 固定 codebook 后用 BERTopic zero-shot 模式（zeroshot_topic_list=codebook）
   ↓        把类别钉住，未匹配的作为"新类候选"人工复核
   ↓        get_topic_info() 拿计数 → 算占比
   ↓        ⚠️ 显式声明占比分母（是否含 HDBSCAN 的 -1 离群点）

⑥ 轴排序    簇心 PCA / semantic projection（两极陈述锚定）/ LLM 两两对立打分
   ↓        输出 {立场, 轴位置, 人数, 占比}
   ↓        ← 全链路唯一"必须从零写"的算法步骤
   ↓        （PCA 路线可直接参考 Red Dwarf：MPL-2.0，复刻 Pol.is 数学管线）

⑦ 呈现      A. 立场坐标轴：Vega-Lite diverging stacked bar（跨中轴百分比）
            B. 立场一览表：改造 Sensemaker report_ui（topic/opinion/引语/占比）
            C. 溯源视图：LLooM Workbench 式"概念→命中数→代表样例→得分理由"
```

### 8.2 关键取舍

| 决策点 | 推荐 | 理由 |
| :--- | :--- | :--- |
| 纯 LLM 归纳 vs 聚类+LLM 命名 | **混合**：LLM 负责"发明/命名/裁定"，向量负责"分组/占比/兜底" | 纯 LLM 是 O(评论数) 成本且不可复现；纯聚类名字不是人话且会把对立立场合并 |
| 类别数 | 由 codebook 固定（6–12 类），而非让 LLM 自由生成 | 你要的是"几个立场类别"，不是几十个长尾话题 |
| 归类方式 | 类别"内容"用 LLM 判定（因为要对立场敏感），占比统计用确定性计数 | 兼顾语义质量与占比准确性 |
| LLM 选型 | 中文强模型（如 DeepSeek/Qwen 系）做抽取与裁定；本地 vLLM + Outlines 约束解码保证 JSON 合规 | 成本与可靠性 |
| 前端 | 短期改造 Sensemaker `report_ui`（Apache-2.0，输入契约只需 4 列 CSV）；长期自建 Vega-Lite 谱系图 | 最快看到"带占比的类别表"，再补坐标轴 |
| 可复现性 | 固定 UMAP `random_state` + 版本化 codebook + 缓存 LLM 输出 + 温度 0 | 否则同一批评论两次跑出不同类别数与占比（BERTopic 官方 FAQ 已明确该风险） |
| "占比"的分母 | 显式定义并对外声明：分母是否包含 HDBSCAN 的 `-1` 离群点 | 否则"占比"含义不明，且官方警告强行归并离群点会把不属于该主题的文档塞进去 |
| 中文分词 | 必须给 BERTopic 换 jieba 版 `CountVectorizer` | 官方 FAQ 明确默认按空格切词，对中文失效，c-TF-IDF 关键词会崩 |
| 技术选型排雷 | **不用 Top2Vec**（停更 22 个月）；**不抄 ClusterLLM 代码**（无 LICENSE）；PromptTopic 无官方实现 | 规避停更与许可风险 |
| 合规 | **不要直接改 BettaFish 代码**（GPL-2.0 + 禁商用）；MediaCrawler 同样禁商用 | 规避许可风险 |

### 8.3 一句话总结

> **"大量子"= 一套自研的"标签抽取 → 归并成 codebook → 固定类别归类 → 立场轴排序"流程 + 三块现成开源件（MediaCrawler 采集、BERTopic 聚类与兜底、Sensemaker report_ui / Vega-Lite 呈现）。**
> 第 1 项需求里最像"现成答案"的 BettaFish 恰恰缺的正是这套流程；真正值得抄的是 **TopicGPT 的提示词流程、LLooM 的概念归纳+prevalence 设计、以及 Sensemaker 从"分类 CSV"到"占比报告"的最后一公里。**

## 9. 对现有《大量子》架构设计的增量建议

> 本节对照工作区中已存在的 `docs/架构设计.md` 与 `daliangzi/prompts/stage1_标签.md`、`stage2_合并.md`、`stage4_坐标轴.md` 撰写。
> **先说结论：现有五阶段设计（①捞标签 → ②语义合并 → ③确定性计数 → ④坐标轴 → ⑤报告）方向是对的，本次调研独立验证了其中的关键判断。** 下面只列"可以改进/可以补强"的点。

### 9.1 独立验证：现有设计中被证实正确的判断 ✅

| 现有设计的判断 | 本次调研的独立验证 |
| :--- | :--- |
| BettaFish 是报告生成器，不含立场归类 | ✅ 已读源码确认：只有 5 级情感极性 + Chart.js 基础图表（见 1.4） |
| Jigsaw「借思路不搬代码」 | ✅ 依赖 `google-genai` / `google-cloud-*`，且官方声明不再积极维护 |
| Talk to the City 架构太重不复用 | ✅ 连本地开发都要求 Firebase + GCS + Redis + Pub/Sub |
| **立场坐标轴没有现成方案，必须自研** | ✅ **系统性检索确认：没有任何开源项目产出"按对立程度排序的一维立场轴"**（见 5.4）。Pol.is 是无标签二维 PCA 且**不能吃自由文本** |
| **中文"标签词捞取"必须自研** | ✅ 无任何开源项目专门做这件事；最接近的 LLooM/TopicGPT 归纳的是**LLM 造的概念名**，不是"评论原文里的词" |
| LLM 只归类、计数交给代码 | ✅ 与 LLooM（系统算 "Number of doc matches"）、BERTopic（簇大小算占比）的做法一致；且 TopicGPT 需要专门的 `correct_topics` 纠错轮来抑制漂移，反证单靠 LLM 一次性分配不可靠 |
| 前端手写 SVG、不引 CDN | ✅ **调研确认"不存在仍在维护的、可直接用的 Likert/立场谱系图组件"**（D3 的 Likert 例子 11★、2014 年停更；`react-likert` 7★、停更 7.5 年）。手写是对的 |
| 采集与分析解耦、适配器层 | ✅ MediaCrawler 的 license 确为自定义非商用许可（API 字段 `NOASSERTION`），且**无库 API**，只能当 CLI/参考实现 |

### 9.2 建议补强 1（最高价值）：stage4 的 x 坐标改为确定性计算

**现状**：`stage4_坐标轴.md` 让 LLM 直接输出每个类别的 `x ∈ [0,1]`，并要求"不要把 8 个类别全挤在 0.45~0.55"。

**风险**（均有来源）：
- LLM 输出的数值**不可复现**，同一批输入两次跑出不同排布；
- 要求"不要挤在中间"等于让模型**制造区分度**，可能产出并不存在的对立；
- 最终轴上位置是"LLM 认为的轴"，缺少与文本证据的绑定，无法回溯。

**建议**（保留 LLM 只做它擅长的"判断轴是什么"）：

1. **LLM 只负责命名轴与两极**（`name` / `left_pole` / `right_pole` + 两端描述）——这是现有 stage4 的第 1、2 步，做得对；
2. **两极文本 + 每个类别的代表原文一起做嵌入**，把类别向量投影到"两极向量张成的轴"上，得到 `x`。这正是 **Semantic Projection / Anchor 法**：
   - 论文：https://www.nature.com/articles/s41562-022-01316-8
   - 参考实现：https://github.com/esfahany/semantic-projection
3. 好处：`x` 变成**确定性、可复现、可追溯到文本**的量；相邻类别的间距有实际语义含义；不再需要"别挤在中间"这种指令。
4. 若坚持纯 LLM 出位置，**至少加一道校验**：验证 `x` 的单调性与"类别–两极相似度差"一致，不一致则打回重排。

> 备选路线（若未来引入投票/打分数据）：第一主成分法，可直接参考 **Red Dwarf**（MPL-2.0，Python 库，复刻 Pol.is 数学管线）：https://github.com/polis-community/red-dwarf

### 9.3 建议补强 2：stage2 先做嵌入预聚类，再让 LLM 合并

**现状**：stage2 把**去重后的全部标签词（可能数百到数千）**一次性喂给 LLM 学出类别。

**风险**：这正会触发你已记录的坑 #2「模型会偷懒合并」——输入越长，漏合并/乱合并的概率越高。

**建议**：两级归约中间插一层**免费的向量预聚**：
1. 对去重标签词做嵌入（bge-m3，MIT，100+ 语言）→ 相似度聚类；
2. 只在"同一预聚簇内 + 相邻簇之间"让 LLM 判定合并，而不是让它面对全量清单；
3. 这同时提供**一致性检查**：LLM 把两个语义相距极远的词合到一起时能被自动标记。

这一模式的现成参考：KeyLLM 官方博客的策略（"**we only extract keywords from 1 document in each cluster and assign the keywords to all documents in the same cluster**"）—— https://www.maartengrootendorst.com/blog/keyllm/ ｜ 文档 https://maartengr.github.io/KeyBERT/guides/keyllm.html
> 注意：若引入 BERTopic 类的聚类，中文必须换 **jieba 分词的自定义 `CountVectorizer`**（官方 FAQ 明确默认按空格切词对中文失效），且 UMAP 要固定 `random_state`——这两点见 3.4。

### 9.4 建议补强 3：引入可量化的质量评测（目前只有"未归类比例"这一指标）

现有设计对 stage1/stage2 的质量只有定性把控（"未归类比例过高就警告"）。调研发现了三件可直接用的评测资产：

| 目的 | 资产 | 用法 |
| :--- | :--- | :--- |
| 评测 **stage1 的 stance 判断** | **C-STANCE**（48,126 条中文微博立场对，比 VAST 大 2.5 倍）：https://github.com/chenyez/C-STANCE ・ 另有 70,931 条中文社媒立场语料 | 抽一个子集，量出"支持/反对/中立/其他"四分类的准确率与混淆矩阵 |
| 评测 **提示词方案优劣** | 论文《Prompting and Fine-Tuning Open-Sourced LLMs for Stance Classification》：https://arxiv.org/html/2309.13734v2 ・ 代码 https://github.com/ijcruic/LLM-Stance-Labeling | 照搬其对比方法，量化不同提示词/是否 few-shot 的差异，而不是凭感觉调 |
| 评测 **stage2 的合并质量** | **TopicGPT 自带 ARI / Harmonic Purity / NMI**：https://github.com/chtmp223/topicGPT | 有人工标注子集时，用这三个指标量化"合出来的类别"与人工分类的一致度 |
| 多语言/多目标立场评测 | **xstance**（MIT，42★）：https://github.com/ZurichNLP/xstance | 交叉验证泛化性 |

补充：**argilla**（5,123★，Apache-2.0，活跃）是成熟的人工复核/标注质控层，如果你想给 stage1/stage2 加一道"抽 200 条人工核对"的流程，不必自己造标注界面。

### 9.5 建议补强 4：直接借鉴这两个"同构"项目的提示词与产物设计

现有设计已经从 Jigsaw 借了"两级分类学 + 引文绑定 + 模拟陪审团"。调研补上两个**同样同构但尚未被引用**的项目：

1. **TopicGPT（NAACL'24，MIT，418★）** —— 五个函数与你的阶段几乎一一对应：
   - `generate_topic_lvl1` / `lvl2` ≈ 你的 **stage2**（学出层级类别）
   - **`refine_topics`（合并近重复 + 删除低频主题）≈ 你的 stage2 核心动作**
   - `assign_topics`（**归类 + 支撑引语 quote**）≈ 你的 **stage1 的 evidence 字段**
   - `correct_topics`（重提示使分配锚定在主题表上）—— **你的架构用"别名映射表 + 纯 Python 计数"替代了这一步，这是比它更稳的设计**，值得在报告里作为设计亮点说明
   - 可 pip 安装（`topicgpt_python`），支持 vLLM 跑开源模型
2. **LLooM（CHI'24，BSD-3-Clause，167★）** —— **本次调研中与你的 stage1+stage2 最同构的学术工作**：
   - 同样是"LLM 归纳出带**自然语言纳入标准**的概念"（对应你的 `canonical` + `core_logic` + `aliases`）；
   - Workbench 展示 **prevalence（占比）**、**Number of doc matches（命中文档数）**、代表样例、**得分理由** —— 与你的 stage3 产物结构一致；
   - 它还有**迭代泛化到更高层概念**的机制，正是你 stage2 的算法骨架，建议精读其归纳循环来加固 stage2 提示词；
   - README 里的对照例子（BERTopic 输出 `"women, power, female"` vs LLooM 输出 `"Criticism of gender roles"`）**可以直接用作你报告里论证"为什么不用话题建模"的引证**。
   - 论文：https://hci.stanford.edu/publications/2024/Lam_LLooM_CHI24.pdf ｜ 代码：https://github.com/michelle123lam/lloom

### 9.6 建议补强 5：报告里应显式声明的"方法论红线"

调研到的学术结论可以直接给你当方法论背书（写进报告或 README）：

- **LLM 能支持但不能替代解释性分析**；主要风险是**偏见、语境丢失、可复现性、模型快速迭代**，需要**持续人工监督**与提示词素养 —— arXiv 2511.14528《LLM-Assisted Thematic Analysis: Opportunities, Limitations, and Recommendations》（25 位 ISERN 研究者的反思工作坊）：https://arxiv.org/abs/2511.14528
- **"占比"必须声明分母**（是否含未归类/离群）。BERTopic 官方文档对离群点的警告可类比：强行把未归类项塞进某类"might force outliers to be put into topics where they do not belong"。你的设计已输出"未归类比例"，建议在报告里**明确写成"本次分析基于 N 条评论，其中 X 条未归入任何立场"**，而不是把未归类默默排除。
- **Sensemaker 的做法值得照搬**：它把兜底类 "Other" **单独输出到一个文件并从最终报告剔除**（`categorized_with_other.csv` vs `categorized_without_other.csv`），同时产出人类可读的 `topic_tree.txt`。你的 `其他零散立场` 类别建议同样"分文件 + 报告里单列"。
- Jigsaw 的约束原则（你已引用）："Every claim or consensus statement must be rooted in the provided text" —— 与你的 `evidence` 铁律同源，可作为对外解释"为什么这个工具不像 AI 瞎编"的正式依据。

### 9.7 建议补强 6：规模上量时的成本逃生舱（现在不必做）

现有 stage1 是 O(评论数) 的 LLM 调用（你已算到 5,000 条约 2~4 元，可接受）。但若将来要跑 10 万条以上，有两条现成的降本范式：

1. **先聚类、每簇只抽一次**（KeyLLM 策略，见 9.3）——把 O(评论数) 压到 O(类别数)；
2. **BERTopic zero-shot 混合模式**：把 stage2 产出的类目名作为 `zeroshot_topic_list`，用**向量余弦相似度**完成绝大多数归类，只有未匹配的评论才回到 LLM；剩余者自动聚成"新类候选"再人工复核。文档：https://maartengr.github.io/BERTopic/getting_started/zeroshot/zeroshot.html
   ⚠️ 代价：向量相似度对"立场对立"不敏感（"支持 X" 与 "反对 X" 向量很近），所以**必须复用你 stage1 已经抽出的 `stance` 字段做二次切分**，不能只靠向量。

### 9.8 一句话给现有设计的结论
