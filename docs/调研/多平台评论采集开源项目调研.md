## 0. 结论速览

| 问题 | 结论 |
|---|---|
| MediaCrawler 能否直接复用 | **功能上可以，法律上不行**。它是 7 平台唯一"一站式"方案且仍在高频维护（最后提交 2026-09-19），但 LICENSE 是 **NON-COMMERCIAL LEARNING LICENSE 1.1**，明确禁止商业用途与大规摸爬取。当作自研工具的依赖模块用于商业产品，需要作者书面授权 |
| 能否独立作为库调用 | **可以 import，但没有官方库 API**。项目是类化模块（`base/`、`media_platform/<platform>/`、`store/`、`database/`），可被 import；但它没发布到 PyPI，官方入口仍是 `main.py` CLI，配套的 `api/main.py`（FastAPI+WebUI）只是 subprocess 包一层 `uv run main.py` |
| 最省事的可用替代 | **按平台各取所需**：抖音=Evil0ctal/Douyin_TikTok_Download_API（20k★，Apache-2.0，自带 REST/MCP，评论+二级评论）；贴吧=aiotieba（685★，匿名即可取楼中楼）；小红书=cv-cat/Spider_XHS（已把签名纯算化，不用浏览器）；微博=dataabc/weibo-crawler（4.6k★）；知乎=cv-cat/ZhihuApis（48★，新） |
| 2026 年最难的平台 | 小红书、抖音、知乎（三平台都要签名逆向/风控对抗）；微博、B 站中等；**百度贴吧最容易** |
| B 站的额外风险 | **B 站相关开源生态在 2026 年被律师函清理**：`SocialSisterYi/bilibili-API-collect`（20.2k★）已 archived 且默认分支改名 `deprecated`；`Nemo2011/bilibili-api`（4.2k★）已公开宣布停止维护并永久关停。B 站采集的"法律风险"已大于"技术风险" |

### 1.4 登录要求

- **默认二维码扫码**：`uv run main.py --platform xhs --lt qrcode --type search`（`--lt` 支持 `qrcode` / `cookie`；WebUI 的下拉项就是 QR Code Login / Cookie Login 两项）。

- 登录态落盘在项目目录的 `brower_data/`；换账号删该目录即可。

### 1.5 风控强度（作者自己的文档怎么说）

来自官方 FAQ（<https://nanmicoder.github.io/MediaCrawler/%E5%B8%B8%E8%A7%81%E9%97%AE%E9%A2%98.html>）原文要点：

- 小红书："**小红书平台风控非常严格，强烈建议使用 CDP 模式连接自己的真实浏览器**（默认配置），不要使用无痕浏览器或标准 Playwright 模式"；扫码后一直卡滑块时建议删 `brower_data/` 重登。
- "爬取失效：出现这种情况多半是由于你的账号触发了平台风控机制了，**请勿大规模对平台进行爬虫**"。
- CDP 常见报错 `Cannot connect to existing browser on port 9222` 的排查步骤（Chrome 版本、远程调试勾选）。

社区侧的封号风险证据（二手）：有实测调研文章引用 **Issue #865「现在小红书风控的力度好像加强了，账号给永久封禁了」**，并称作者对风控类 issue 打标签"风控问题不处理"，建议"永远不要用主账号，用专门的小号 + IP 代理，控制并发频率"。
来源：<https://blog.csdn.net/wukuncsdn/article/details/163608681>

平台侧的风控升级在**仓库提交记录里有第一手证据**（抖音 2026-09 引入 ArgusSecurityPlugin、强制 uifid/verifyFp/x-tt-argus 请求头）——见 1.1 的提交列表。

### 1.6 能否独立作为库调用？

结论：**结构上可 import，工程上不建议当"库"依赖。**

- 有清晰的抽象基类：`AbstractCrawler` / `AbstractLogin` / `AbstractStore` / `AbstractApiClient`，并按平台分模块 `media_platform/{xhs,dy,ks,bilibili,wb,tieba,zhihu}/`、`store/<platform>/`、`database/models.py`（ORM）。
  来源：<https://ghproxy.net/https://raw.githubusercontent.com/NanmiCoder/MediaCrawler/main/base/base_crawler.py>、代码结构文档 <https://nanmicoder.github.io/MediaCrawler/%E9%A1%B9%E7%9B%AE%E4%BB%A3%E7%A0%81%E7%BB%93%E6%9E%84.html>
- 但官方入口只有 CLI：`uv run main.py --platform xhs --lt qrcode --type search`，配置全部走 `config/base_config.py` 的全局变量（关键词、指定 ID 列表、开关），**没有 SDK 风格的 `client.get_comments(...)` 公共 API，也没有版本化契约**。
- 新增的 WebUI/API 服务（`uvicorn api.main:app --port 8080`）是**进程包装**：`/api/env/check` 直接 `subprocess.run(["uv", "run", "main.py", "--help"])`，`crawler_router` 负责拉起爬虫进程，`/api/config/*` 返回平台与选项枚举。它是"远程控制台"，不是"数据 API"。
- **PyPI 上没有包**（<https://pypi.org/pypi/mediacrawler/json> → 404），`pyproject.toml` 里也没有 `[project.scripts]` 之类的入口。

### 1.7 数据落库格式

官方存储指南（<https://ghproxy.net/https://raw.githubusercontent.com/NanmiCoder/MediaCrawler/main/docs/data_storage_guide.md>）列出：

| 方式 | 参数 | 说明 |
|---|---|---|
| JSONL | `--save_data_option jsonl` | **默认格式**，每行一个 JSON 对象，追加写性能好 |
| JSON | `--save_data_option json` | 落在 `data/` |
| CSV | `--save_data_option csv` | 落在 `data/` |
| Excel | `--save_data_option excel` | 多工作表（内容/评论/创作者）、格式化列宽 |
| SQLite | `--init_db sqlite` + `--save_data_option sqlite` | 推荐个人使用 |
| MySQL | `--init_db mysql` + `--save_data_option db`（历史参数名） | 需先建库 |
| PostgreSQL | `--init_db postgres` + `--save_data_option postgres` | 推荐生产 |
| MongoDB | WebUI 选项里有 `mongodb`（依赖 `motor`） | README 主表未展开 |

注意一处**文档不一致**：README 的"数据保存"段只写 CSV/JSON/JSONL/Excel/SQLite/MySQL，**存储指南另加 PostgreSQL**；而第三方调研文章把 MongoDB 也列进去。以 `docs/data_storage_guide.md` 与 `api/main.py` 的枚举为准更稳妥。

字段层面：`database/models.py` 定义 ORM 模型 + `model/m_*.py`（如 `m_xiaohongshu.py`、`m_douyin.py`、`m_weibo.py`、`m_zhihu.py`、`m_baidu_tieba.py`、`m_kuaishou.py`）是各平台的数据模型；README 未给出逐字段清单，**要字段级 schema 必须自己读 `model/` 与 `database/models.py`**。

| 平台 | 难度 | 主要门槛（证据） | 采集评论可行路线 |
|---|---|---|---|
| **小红书** | 🔴 极难 | 签名链最长（a1/b1/websectiga/x-s/x-t/x-s-common/x-rap-param/gid…），有 406 概率闸门；风控最严，官方 FAQ 明说"风控非常严格…建议 CDP 真实浏览器"；社区有**永久封号**案例（Issue #865） | Spider_XHS（纯算签名，不用浏览器）或 MediaCrawler CDP 模式；账号务必用小号 |

## 5. 如果要在一个自研工具里复用：最实际的方案

### 5.1 分层建议（按"取评论"这件事的组织方式）

1. **优先买评论、自己只做编排**：抖音/微博直接用官方开放平台或 TikHub；能签合同的场景把"采集"外包给成品 API，自研工具只做调度、去重、清洗、入库。理由：抖音 2026 年 Argus 风控与小红书签名链的维护成本是**持续性**的（MediaCrawler 9 月连续三天提交都在补风控参数），自研等于接下一个永久的运维负担。
2. **开源复用按平台选，不追求"一套全包"**：
   - 贴吧 → **aiotieba**（匿名、纯库、最稳，`get_comments` 直接拿楼中楼）。
   - 抖音 → **Douyin_TikTok_Download_API**（Apache-2.0，可商用，自带 REST/MCP，评论+回复；代价是 docker compose + PostgreSQL/Redis）。
   - 小红书 → **Spider_XHS**（无浏览器、签名本地纯算、有库式调用与 Excel 输出）。若你已在用 MediaCrawler 且只是自用学习，则继续用它的小红书模块即可。
   - 微博 → **weibo-crawler**（注意评论只在 sqlite 模式下产出，字段与 csv 不同，入库前要单独处理）。
   - 知乎 → **ZhihuApis**（新、小，但定位正好是"评论+楼中楼"，走 FastAPI+Cookie，最容易接进自带服务）。
   - B 站 → 只有两条路：MediaCrawler 的 bilibili 模块（自用/学习），或商业 API（TikHub 有 Bilibili 评论端点）。**不要把 `bilibili-API-collect` / `bilibili-api` 作为技术栈，它们已经关停**。
3. **MediaCrawler 的定位建议**：把它当**参考实现 + 学习资料**，而不是生产依赖。若确实要用它的代码，必须同时满足：非商业用途、控制频率不做大规模爬取、保留版权与许可声明；否则需联系作者取得书面授权（作者另有付费 MediaCrawlerPro）。

### 5.2 如果坚持用 MediaCrawler 的工程注意点

- 用**独立小号**，不要用主账号；配合代理池，把并发压到最低（README 与 FAQ 都强调"请勿大规模对平台进行爬虫"）。
- 开评论要改 `config/base_config.py` 的 `ENABLE_GET_COMMENTS`（默认关闭），别以为跑完就有评论数据。
- 默认走 **CDP 连接真实 Chrome**（Chrome >= 144 + 手动点"接受"），这是它降低风控的核心手段；标准 Playwright 模式更容易被识别。
- 抖音/知乎要装 **Node.js >= 16**，否则 `pyexecjs` 会以 `SyntaxError: 缺少 ';'` 之类的怪错炸掉。
- 落库默认 **JSONL**；要 SQLite/MySQL/PostgreSQL 得先 `--init_db <type>`。
- 它**不发布 PyPI 包**，意味着你要么 git submodule/vendor 源码、要么 subprocess 调 CLI；想在自己的进程里"当库调用"，只能自己写 adapter 包住 `media_platform/*`，并承担内部接口随时变的风险。

### 5.3 一句话结论

> 评论采集的现实是"**没有一套开源方案能同时满足：7 平台 + 可商用 + 可当库 + 稳定**"。
> 最实际的组合是：**贴吧用 aiotieba、抖音用 Douyin_TikTok_Download_API、小红书用 Spider_XHS、微博用 weibo-crawler、知乎用 ZhihuApis、B 站走商业 API**，在自研工具里用统一的 adapter 层（平台适配器 → 统一 comment schema → 去重/增量 → 存储），把"签名与风控"这一层成本留在各上游项目里，而不是自己重写一遍。
